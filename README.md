# Nestside

## 개발용 파일 삭제와 장애 복구

`DELETE /files/{file_id}`는 기본 비활성화이며 `403`을 반환합니다.
서버 프로세스에 다음 두 설정을 모두 명시한 경우에만 활성화됩니다.
인증은 아직 없으므로 신뢰할 수 있는 로컬 개발 환경에서만 사용하세요.

```bash
NESTSIDE_ENV=development NESTSIDE_ENABLE_DELETE=true .venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1
```

### 업로드와 삭제의 공통 잠금

Linux 로컬 파일시스템의 `flock`으로 파일명별 프로세스 간 잠금을 사용합니다.
동일 이름의 업로드·삭제·복구가 겹치면 대기하지 않고 `409`를 반환합니다.
서로 다른 이름은 별도의 잠금을 사용하며, 업로드의 파일 생성부터 DB 커밋까지,
삭제의 검증부터 커밋·정리까지 잠금을 유지합니다. 실행 중인 구버전 서버는 이 잠금을
사용하지 않으므로 배포할 때 모든 워커를 교체해야 합니다.

잠금과 작업 기록은 `storage/.nestside-operations/<파일명 SHA-256>/`에 저장합니다.
잠금 파일은 삭제하지 않습니다. `.nestside-*` 및 `.delete-quarantine` 이름은
내부용으로 예약됩니다. 기존 정상 API의 경로와 성공 응답 형식은 유지됩니다.
서버 시작 시 저장소를 생성하며, 모듈을 읽는 것만으로 저장소를 생성하지 않습니다.

### 삭제와 복구 기록

파일 ID를 조회해 잠금 키를 얻은 뒤, 잠금을 획득하고 DB 행을 다시 조회해 잠급니다.
파일은 저장소 바로 아래 일반 파일만 허용하며 경로 순회와 심볼릭 링크를 거부합니다.
저장소와 내부 디렉터리는 `O_NOFOLLOW`로 열고 디렉터리 디스크립터 기준으로 작업합니다.
DB 크기·SHA-256과 실제 파일을 비교하고, 이동 전후 장치 번호·inode·크기·해시도 확인합니다.

`record.json`에는 작업 UUID, 종류, 파일명, 파일 ID(삭제), 식별 정보, 처리 단계가 들어갑니다.
기록은 임시 파일 쓰기 → 파일 fsync → 원자적 교체 → 디렉터리 fsync 순서로 갱신합니다.
파일을 `payload`로 격리하고 관련 디렉터리를 동기화한 뒤 DB 행을 삭제합니다.
커밋 의도를 기록하고 커밋이 확인되면 payload와 기록을 정리합니다.
성공 응답은 `{"id": 1, "status": "deleted", "cleanup_pending": false}`입니다.
커밋 후 정리만 실패하면 `cleanup_pending: true`를 반환하며 기록을 보존합니다.
DB 스키마 변경은 필요하지 않습니다.

DB DELETE 실패 시 롤백을 확인한 후 원래 파일을 덮어쓰지 않는 하드 링크로 복원합니다.
롤백 실패, 이동·동기화 오류, 커밋 응답 유실, 프로세스 중단 시 기록과 파일을 보존하고
해당 이름의 후속 업로드·삭제를 차단합니다. 업로드도 생성 전 기록을 남깁니다.
업로드 DB 결과가 불확실하면 파일을 삭제하지 않고 기록과 함께 보존합니다.

### 명시적 복구 도구

자동 시작 복구는 하지 않습니다. 다음 명령은 사용법 예시이며 자동 실행되지 않습니다.
먼저 파일 작업을 중지하고 이전 서버 프로세스와 DB 세션이 종료됐는지 확인하세요.
복구 도구는 저장소 경로를 필수로 받으며 DB에 INSERT/UPDATE/DELETE를 실행하지 않습니다.

```bash
# 기록 확인: DB에 접속하지 않음. 잠금용 내부 디렉터리/파일은 생성될 수 있음.
.venv/bin/python -m backend.recovery --storage /path/to/storage --filename example.txt
# 관리자 확인 후 명시적으로 복구 적용
.venv/bin/python -m backend.recovery --storage /path/to/storage --filename example.txt --apply
```

삭제 작업의 DB 행이 식별 정보와 일치하면 원본을 복원합니다. 행이 없고 원래 경로도
비어 있으면 검증된 격리 파일을 정리합니다. 업로드는 DB 행과 실제 파일이 일치할 때만
완료로 확인하고 기록을 정리합니다. 부분 업로드나 DB 행이 없는 업로드는 보존하며
관리자가 확인해야 합니다. 기존 경로에 다른 파일이 있거나 DB 중복·불일치, 해시 변경,
심볼릭 링크, 손상된 기록 등이 있으면 파일을 보존하고 오류로 관리자 확인을 요청합니다.
구버전 `.delete-quarantine` 기록은 자동 변환하지 않고 해당 이름을 차단합니다.

복구 전 파일과 기록을 별도로 보관하세요. 기록을 무조건 지우거나 원본에 덮어쓰지 마세요.
파일 손실 또는 디스크 자체 장애를 복구하는 백업 시스템은 아닙니다. 파일시스템과 DB의
원자적 단일 트랜잭션을 제공하지 않으며, 불확실한 상황은 수동 확인으로 남깁니다.

### 격리 자동 테스트

```bash
.venv/bin/python -B -m unittest backend.test_delete backend.test_stability -v
```

테스트는 임시 저장소와 모의 DB만 사용하며 운영 DB·실제 storage는 사용하지 않습니다.
동시 업로드·삭제, 다른 이름의 독립성, 별도 프로세스 잠금, DB 오류, 이동·기록·복원 실패,
프로세스 강제 종료 후 재시작, 경로·심볼릭 링크 차단, 기존 API 회귀를 확인합니다.
`backend/test_db.py`는 운영 연결 스크립트이므로 테스트 전체 검색 대신 위 모듈을 명시하세요.

잠금은 같은 로컬 저장소를 공유하는 Linux 서버 워커를 전제로 합니다. NFS/다중 호스트,
저장소를 직접 수정하는 외부 프로그램, 실제 PostgreSQL 장애·전원 단절 환경은 검증하지
않았습니다. 전체 파일 해시 확인에는 파일 크기에 비례하는 시간이 필요합니다. 다운로드와
목록은 잠금을 사용하지 않으므로 삭제 중 일시적인 목록·다운로드 불일치는 남을 수 있습니다.

### AI 기반 지능형 개인 클라우드 스토리지 시스템

Nestside는 개인 Ubuntu 서버를 기반으로 구축하는 클라우드 스토리지 시스템입니다.

사용자가 자신의 서버에 파일을 저장하고, 웹을 통해 파일을 관리하며,
PC 간 파일 동기화와 AI 기반 파일 검색 및 저장공간 관리 기능을 제공하는 것을 목표로 합니다.

## 주요 기능

- **파일 관리**: 파일 업로드, 다운로드 및 저장소 관리
- **파일 동기화**: PC와 서버 간 파일 자동 동기화
- **AI 파일 관리**: 자연어를 활용한 파일 검색 및 분석
- **메타데이터 관리**: 파일 정보 및 저장공간 상태 관리
- **안정적인 파일 전송**: 대용량 파일 전송 및 중단된 전송 재개

## 기술 스택

- **Server**: Ubuntu
- **Backend**: Python, FastAPI, Uvicorn
- **Frontend**: Next.js, React (예정)
- **Database**: PostgreSQL (예정)
- **Version Control**: Git, GitHub
