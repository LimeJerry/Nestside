# Nestside 개발 현황 및 로드맵

기준일: **2026년 10월 20일**

이 문서는 해당 기준일의 실제 소스와 격리 테스트 결과를 바탕으로 한다.
목표·예정과 완료를 구분하며, 운영 배포 상태나 운영 DB 내용은 확인하지 않았다.
공통 작업 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

## 현재 구현된 기능

| 기능 | 상태 및 확인 근거 |
| --- | --- |
| 서버 응답 확인 | GET / 구현 |
| 파일 업로드 | POST /upload, 1MiB 청크 저장, 크기·SHA-256 계산, 메타데이터 INSERT |
| 파일 다운로드 | GET /download/{filename}, 파일 존재 확인 후 FileResponse 반환 |
| 파일 목록 | GET /files, DB의 메타데이터를 최신순으로 반환 |
| PostgreSQL 연결 | database.py에서 환경변수 기반 psycopg 연결 생성 |
| ID 기반 파일 삭제 | DELETE /files/{file_id}, 메타데이터·파일 대조 및 격리 삭제 |
| 삭제 활성화 제한 | 기본 비활성화; 개발 환경 설정과 명시적 활성화가 모두 필요 |
| 파일명별 공통 잠금 | 업로드·삭제·복구에서 Linux flock 사용, 충돌 시 409 |
| 영속 작업 기록 | UUID·처리 단계·식별 정보 기록, fsync 및 원자적 교체 |
| 장애 복구 도구 | recovery.py의 명시적 CLI 및 recover_file 구현; 충돌 시 보존 |
| 웹 UI | Next.js 16.4.2 · TypeScript · Tailwind CSS 4.3.3 기반 목록·업로드·다운로드·삭제 확인 구현 |
| 삭제 UI | 파일명·복구 경고 확인창, 중복 요청 방지, 비활성화·오류·정리 대기 안내 |
| PC 동기화·AI 검색·인증 | 미구현 |

SHA-256 계산과 서버 측 파일·메타데이터 비교는 구현되어 있다. 클라이언트가 보낸
기대 해시를 검사하는 전송 무결성 검증, 분할 업로드, 중단 전송 재개는 구현되지 않았다.
대용량 파일에 대한 운영 성능·용량 한계 검증도 완료로 보지 않는다.

## 현재 시스템 아키텍처

```text
Windows 등 내부망 브라우저 → Next.js frontend/ (0.0.0.0:3000)
  → /api/files, /api/files/{file_id}, /api/download/{filename}: 외부 rewrites
  → /api/upload: 내부 rewrite → 스트리밍 Route Handler
  → Ubuntu loopback 127.0.0.1:8000 → FastAPI: backend/main.py
      → 업로드·삭제: file_operations.py의 파일명별 잠금과 작업 기록
          → 로컬 storage/: 파일 본문 및 격리 payload
          → database.py → PostgreSQL files: 파일 메타데이터
      → 다운로드: storage/ 파일 직접 응답
      → 목록: PostgreSQL 메타데이터 조회
관리자 명시적 복구: recovery.py → 같은 잠금 → DB·파일 대조 → 복원 또는 정리
```

- 파일 본문과 DB 메타데이터를 분리한다. SQL에 사용되는 컬럼은 id, filename, size,
  sha256, content_type, uploaded_at이다. 스키마 생성·마이그레이션 파일은 확인되지 않았다.
- DB 연결은 호출마다 생성하며 연결 풀은 없다. 실제 컬럼 타입·제약조건·인덱스는 미확인이다.
- 파일명별 작업 디렉터리는 storage/.nestside-operations/ 아래에 있다. 런타임 데이터이며
  Git에 넣지 않는다. .nestside-* 및 .delete-quarantine 이름은 예약되어 있다.
- 삭제는 DB ID로 이름을 조회한 뒤 파일명 잠금을 얻고 DB 행을 다시 조회·잠근다.
  크기·해시와 파일 식별 정보를 확인하고 파일 격리 → DB 삭제·커밋 → 파일 정리를 수행한다.
- 파일시스템과 DB가 하나의 원자적 트랜잭션인 것은 아니다. 중간 상태는 영속 기록과
  재사용 차단으로 보존하고, 관리자 복구로 조정한다. 자동 시작 복구는 없다.
- 복구 CLI는 DB 조회·행 잠금만 수행하지만 --apply는 실제 파일을 변경할 수 있다.
  승인 후 이전 서버 프로세스·DB 세션 종료와 대상을 확인해야 한다. 조회 모드도
  내부 잠금 디렉터리·파일을 생성할 수 있다.

## 테스트 결과

2026년 10월 20일 현재 코드에서 다음 명령을 재실행했다.

```bash
.venv/bin/python -B -m unittest backend.test_delete backend.test_stability
```

백엔드 재검증 결과: **40개 통과** — test_delete.py 16개, test_stability.py 24개.

검증한 범위:

- 기존 루트·업로드·다운로드·목록 API, 중복 업로드 및 없는 파일 처리.
- 삭제 기본 비활성화, ID 오류, 메타데이터 불일치, 일반 파일·경로·심볼릭 링크 검사.
- 동시 업로드·삭제 충돌, 서로 다른 이름의 독립성, 별도 프로세스 간 잠금.
- DB 삭제·롤백·커밋 오류, 파일 이동·디렉터리 동기화·기록 갱신 실패.
- 격리 파일 보존, 복원·정리 실패 후 재시도, 경로·DB 충돌 및 손상 기록 보존.
- 별도 프로세스의 비정상 종료 후 기록 유지와 복구, 불완전 업로드의 관리자 확인 요구.

임시 저장소와 모의 DB만 사용했다. 운영 PostgreSQL 통합 테스트, 실제 전원 단절,
운영 데이터 변경 여부의 전후 스냅샷 비교를 수행한 결과는 아니다.
backend/test_db.py는 설정된 DB에 접속하는 별도 확인 스크립트이므로 실행하지 않았다.

### 프론트엔드 검증

frontend/에서 Node 22.23.3·npm 11.21.1 환경으로 검증했다.

```bash
npm test
npm run lint
npm run build
npm run typecheck
PLAYWRIGHT_BROWSERS_PATH=/tmp/nestside-playwright npm run test:e2e
```

- 단위·컴포넌트·스트리밍·삭제 UI/API: **55개 통과** (초기 UI 29개에서 확장).
- Linux Chromium 브라우저 통합: **17개 통과** (기존 회귀 8개 + 삭제 UI 9개).
- ESLint, TypeScript, 프로덕션 빌드 통과. 운영 의존성 npm audit 취약점 0건 확인.
- 임시 파일·모의 DB 기반 별도 FastAPI 앱(18080)과 별도 Next.js(13100)를 자동 실행했다.
  운영 8000 서버, 운영 PostgreSQL 및 실제 storage/를 테스트에 사용하지 않았다.
- 16MiB 파일 업로드·다운로드의 SHA-256 일치, 4MiB 청크 요청이 완료되기 전에 백엔드에
  전달되는 동작, 특수문자 파일명, 충돌, 빈 목록·서버 오류, 모바일 가로 넘침을 확인했다.
- 자동 브라우저 테스트의 화면 캡처도 확인했다. 이후 승인된 Windows 수동 삭제 통합 테스트와
  파일·PostgreSQL 검증을 완료했다. GB급·동시 대용량 메모리 상한과 일반 운영 장애는 미검증이다.

### 프론트엔드 전송 경로

설치된 Next.js 16.4.2의 외부 rewrite는 본문 복제와 기본 10MiB 제한이 적용된다.
따라서 업로드는 rewrite로 내부 /internal/upload에 연결하고 request.body를 파싱·전체
버퍼링하지 않는 스트리밍 핸들러가 FastAPI에 전달한다. 다운로드는 일반 링크와 외부
rewrite로 전달한다. 브라우저 파일을 base64·전체 ArrayBuffer·다운로드 Blob으로 만들지 않는다.
백엔드 프로그램과 DB 스키마는 변경하지 않았다. 설정·실행 절차는
[frontend/README.md](../frontend/README.md)에 있다.

### 삭제 UI 보완 및 검증

- 각 파일의 삭제 버튼 → 파일명과 복구 미보장 경고 → 명시적 확인 → ID 기반 DELETE로 연결한다.
- 취소 기본 초점, 탭 순환, Esc 취소, 종료 후 초점 복귀를 검증했다. 요청 중에는 중복 확인·
  취소·업로드를 차단한다. 새 사용자 문구와 새 주석은 한국어로 작성했다.
- 성공 응답의 ID·상태·cleanup_pending을 검증하고 목록·파일 수·전체 용량을 갱신한다.
  재조회 실패가 확인된 삭제를 되돌리지 않도록 마지막 목록에서도 해당 ID를 제거한다.
- 403 비활성화, 404 파일 없음, 409 충돌·복구 확인, 서버·네트워크 오류·잘못된 응답을 구분한다.
  1분 대기 후에도 결과가 없으면 불확실성을 안내하고 자동 재삭제하지 않는다. 서버 처리는
  브라우저 대기 종료 뒤에도 계속될 수 있다. cleanup_pending은 관리자 정리 확인으로 안내한다.
- 테스트 서버의 모의 DB에 삭제용 조회·트랜잭션 동작을 추가했다. 기본은 비활성화이며
  테스트 전용 제어 경로로 해당 격리 프로세스만 활성화한다. 운영 .env는 변경하지 않았다.
- 실제 임시 파일 삭제 후 다운로드 404·메타데이터 제거·파일 수와 용량 갱신을 확인했다.
  취소 무요청, 기본 비활성화 보존, 중복 차단, 오류별 안내, 정리 대기 응답도 브라우저 검증했다.
- backend/와 PostgreSQL 스키마는 변경하지 않았다. 기존 업로드·다운로드·목록, 16MiB 왕복과
  스트리밍 회귀도 통과했다. 운영 데이터 대상 테스트·삭제, Git commit/push는 수행하지 않았다.

- 실제 파일 본문, 비밀정보, 비교 스냅샷, 운영 DB 덤프는 Git에 포함하지 않는다.

## 2026년 10월 25일 목표: Nestside Web MVP v0.1

목표일은 유지한다. Next.js + TypeScript + Tailwind CSS를 선택해 초기 UI를 구현했다.
목록·업로드·다운로드의 격리 검증 및 Windows 내부망 접속·승인된 실제 삭제 검증을 완료했다.
초기 UI 단계에서 제외했던 삭제 UI는 별도 승인 후 구현·격리 검증했다.
인증 없는 외부 공개 또는 운영 준비 완료를 의미하지 않는다.

| 우선순위 | 다음 작업 | 완료 판단 기준 |
| --- | --- | --- |
| 1 | 웹 UI 프로젝트 구성 | 완료: frontend/, 고정된 의존성 잠금 파일, 별도 Node 22 런타임, 개발 서버 설정 |
| 2 | 파일 목록 표시 | 완료: 목록·이름·크기·한국 시각, 새로고침·로딩·빈 목록·오류 처리 |

삭제 UI 때문에 백엔드 삭제 정책을 완화하지 않는다. 개발용 임시 데이터로 검증하며,
인증 없는 MVP의 외부 공개나 운영 삭제 활성화를 완료 기준에 포함하지 않는다.
브라우저는 Next.js의 상대 API 경로를 사용하므로 CORS 미들웨어는 추가하지 않았다.
Next.js 기본 대상은 http://127.0.0.1:8000이며, 테스트에서는 별도 loopback 포트를 사용한다.
기본 개발 접속 주소는 http://172.30.1.46:3000 이다. 이번 Windows 수동 검증에서는
실행 중인 13000 프론트엔드 → 127.0.0.1:8000 FastAPI 경로의 접속·삭제를 확인했다.

## 이후 개발 예정

- PC 자동 동기화: 클라이언트, 변경 감지, 충돌 처리, 재시도·재개 정책 설계.
- AI 파일 검색: 검색 대상·메타데이터·인덱싱·모델 연동 및 개인정보 처리 방안 설계.
- 인증 및 보안 강화: 사용자 인증, 파일 소유권·권한, 안전한 운영 공개 구성.
  외부 공개나 운영 삭제에 앞서 우선 검토하며 MVP 목표 때문에 생략하지 않는다.
- 업로드 용량 제한·할당량, 목록 페이지네이션, DB 마이그레이션·연결 풀 검토.
- 분리된 PostgreSQL 테스트 환경, 실제 트랜잭션·장애 복구 통합 검증.

## 알려진 제약 및 미해결 문제

- 인증·소유권 검사가 없다. 현재 삭제 제한은 인증 기능을 대체하지 않는다.
- 경로·심볼릭 링크 방어는 업로드·삭제·복구 중심이다. 다운로드는 is_file과
  FileResponse를 사용하며 동일한 수준의 저장소 경계·링크 검증이 없다.
- 다운로드·목록은 공통 잠금을 사용하지 않으므로 삭제 중 일시적 불일치가 가능하다.
- 파일명 잠금은 같은 로컬 저장소를 쓰는 Linux 워커를 전제로 한다. NFS·다중 호스트와
  잠금을 따르지 않는 외부 프로그램의 직접 파일 변경은 검증하지 않았다.
- 불완전 업로드, 커밋 결과 불확실성, 기록 손상·충돌은 수동 확인이 필요할 수 있다.
  구버전 .delete-quarantine 기록은 자동 변환하지 않는다.
- 잠금 파일은 유지하며, 기록 교체 전 중단으로 남는 임시 기록의 정리 정책은 별도 과제다.
- 동기 파일 I/O·해시 계산·DB 호출을 async 업로드에서 수행한다. 대용량·다중 요청의
  이벤트 루프 지연 가능성이 있으며 성능 테스트가 필요하다.
- 업로드 용량 제한·할당량, 목록 페이지네이션, 전송 재개가 없다.
- 저장소·DB의 실제 스키마 및 배포 환경을 이 문서 작성 과정에서 변경하거나 검증하지 않았다.
- 인증·전송 재개는 프론트엔드에도 없다. 다운로드 실패 시 오류 JSON이 파일로
  저장될 수 있으며, Windows에서 허용되지 않는 파일명 문자는 브라우저가 치환할 수 있다.
- 시스템 Node 18은 유지했다. 새 터미널에서는 프로젝트 내부 Node 22 런타임을 활성화해야 한다.
- Windows LAN 연결과 승인된 단일 파일의 PostgreSQL 연계 삭제는 확인했다. GB급 전송,
  장시간·동시 요청 성능과 일반적인 PostgreSQL 장애·복구는 미검증이다.

## 최근 작업 기록과 다음 우선순위

2026년 10월 20일 기준 작업 순서이며, 개별 구현의 정확한 일시는 별도로 단정하지 않는다.

1. 기존 API·DB 연결·파일 흐름 분석 및 위험 요소 검토.
2. ID 기반 삭제 API, 기본 비활성화, 격리 삭제·초기 복구 및 16개 테스트 구현.
3. 경쟁 상태·중단 복구 검토 후 업로드·삭제·복구 공통 잠금과 영속 기록 보완.
4. 동시성·장애·재시작 검증을 포함한 격리 테스트 총 40개 통과.
5. AGENTS.md와 본 문서 작성, 현재 소스 확인 및 40개 테스트 재실행.

6. Next.js 웹 UI 구성, 목록·업로드·다운로드, 스트리밍 핸들러 및 격리 프론트엔드 테스트 구현.
7. 백엔드 40개·프론트엔드 29개·브라우저 8개 검증과 실행·내부망 안내 및 현황 갱신.
8. 승인된 삭제 UI 구현 및 백엔드 40개·프론트엔드 55개·브라우저 17개 회귀 검증, 안전한 수동 브라우저 검증 절차 갱신.
9. 승인된 Windows 실제 삭제·파일/DB 보존 검증 성공 및 삭제 비활성화 환경 확인. GitHub 저장 전 최종 검증과 커밋 대상 점검.

다음 우선순위는 승인된 별도 환경의 성능·장애 검증 →
인증·권한 및 다운로드 안전성 보완이다. 삭제 UI는 별도 승인 범위로 구현을 완료했다.
개발 완료 때마다 이 문서의 완료 항목, 테스트 결과, 제약과 다음 우선순위를 갱신한다.
이 문서는 배포·커밋·push 완료를 의미하지 않는다.
